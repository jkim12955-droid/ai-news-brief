# AI 뉴스 브리핑

한국어 AI 뉴스를 하루에 한 번 모아서, 읽을 값이 있는 것만 골라 아침 브리핑 한 장으로 만드는 자동화다. GDELT 가 15분마다 올리는 번역 수집 원본 파일(GKG) 96개에서 어제 하루치 한국어 기사 가운데 제목에 AI 관련어가 든 것을 받아 스스로 점검한 다음 sqlite 에 쌓고, 제목만 보고 AI 소식인지 가려내 같은 사건끼리 묶는다. 결과는 마크다운 브리핑으로 떨어지고 슬랙으로 나간다. 월요일에는 지난 한 주를 키워드별로 센 리포트와 차트를 하나 더 만든다. 한국 시간 아침 9시부터 11시 40분까지 20분마다 시도해 그날 몫을 보낼 때까지 돌리고, 사람은 브리핑을 읽고 키워드 목록을 손보는 일만 한다. 외부 패키지는 차트를 그릴 matplotlib 하나뿐이고, 나머지는 파이썬 표준 라이브러리로만 돌아간다.

먼저 밝혀 둘 것이 있다. `data/briefs` 의 브리핑은 2026-09-13 치부터 GitHub Actions 가 날마다 실제로 돌려 슬랙과 노션으로 보낸 것이고, 언제 어느 실행이 보냈는지는 `data/sent` 에 남는다. 그보다 앞선 2026-09-09 와 09-12 두 장도 GDELT 에서 실제로 받은 응답으로 만들었다. 손으로 지어낸 표본은 `tests/fixtures` 의 09-10 과 09-11 두 파일, 그리고 그것으로 만든 주간 리포트 `data/reports/2026-09-07` 하나뿐이다. DB 와 원본 응답은 저장소에 올리지 않는다. 어느 파일이 어느 쪽인지는 아래 [지금 저장소에 든 자료](#지금-저장소에-든-자료) 에 표로 적었다.

## 하루가 도는 순서

한 번 실행하면 일곱 단계를 차례로 지난다. `python3 -m news_brief run` 이 이 전부를 한 번에 돈다.

1. **수집** (`collect.py`, `gdelt.py`)
   한국 날짜 하루를 UTC 구간으로 바꿔 GDELT 를 부른다. 한 번에 250건이 상한이라, 받은 건수가 상한에 딱 걸리면 뒤가 잘렸다고 보고 시간 구간을 절반으로 쪼개 다시 받는다. 기본 네 번까지 쪼개니 하루가 90분 토막까지 나뉜다. 설정으로 더 깊게 적어도 코드가 다섯에서 끊는다. 요청 사이에는 5초를 쉰다. 그래도 GDELT 가 429 로 막는 날이 있어서 12초, 24초, 48초를 쉬고 세 번까지 다시 부른다. 세 번 다 막힌 구간은 그 구간만 접고 나머지를 계속 받은 다음 못 받았다고 적어 남긴다. 받은 응답은 구간마다 곧바로 `data/raw/<날짜>.partial.jsonl` 에 이어 쓰고, 하루치를 다 받으면 `data/raw/<날짜>.json` 한 장으로 정리한다. 중간에 끊겨도 앞서 받아 둔 응답이 남는다.

2. **적재 전 점검** (`qa.py`)
   받아 온 것만으로 볼 수 있는 멈춤 조건 다섯 가지를 먼저 본다. 여기서 실패가 나오면 DB 에 아무것도 넣지 않고 종료 코드 1 로 멈춘다. 이 순서에는 까닭이 있다. `store.py` 는 링크를 기본키로 쓰고 한 번 들어간 기사의 날짜를 나중 실행이 덮어쓰지 않기 때문에, 날짜가 어긋난 기사가 한 번 들어가면 원인을 고친 뒤에도 영원히 잘못된 날에 매달려 집계와 리포트에 섞인다. 넣기 전에 거를 것은 넣기 전에 거른다.

3. **적재** (`store.py`)
   제목의 군더더기 공백을 덜어 내고 같은 링크를 한 건으로 줄인 다음 `data/news.db` 에 넣는다. 링크를 열쇠로 삼아 같은 날짜를 몇 번 돌려도 같은 기사가 두 줄로 쌓이지 않는다.

4. **판단** (`judge.py`)
   제목만 보고 AI 소식인지 가린다. 뺀 기사에는 왜 뺐는지 한국어 한 문장을 남긴다. 남은 기사는 제목 낱말이 겹치는 비율로 같은 사건끼리 묶고, 묶음마다 새 도구 소식인지 규제나 정책 소식인지 가려 한 줄 문장을 붙인다. 판단 결과는 DB 에 남는다. 같은 날짜를 같은 기사로 다시 돌리면 저장된 판단을 그대로 읽어 쓰므로 몇 번을 돌려도 숫자가 흔들리지 않는다. 다시 수집해 기사가 늘어났거나 요청한 백엔드가 달라졌으면 저장된 판단을 버리고 다시 판단하고, 그 까닭을 화면에 적어 준다.

5. **전체 점검** (`qa.py`)
   적재와 판단을 마친 자료로 열한 가지를 본다. 아래 표에서 실패로 적힌 여섯 가지가 하나라도 걸리면 브리핑을 만들지 않고 종료 코드 1 로 멈춘다. 틀린 브리핑을 내보내는 것보다 아무것도 내보내지 않는 편이 낫다는 판단이다. 멈출 때는 무엇이 어긋났는지 슬랙으로 알린다. 판단을 이 앞에 둔 까닭도 있다. 걸러낸 비율 점검은 판단 결과가 있어야 재는데, 점검이 판단보다 먼저면 그 날짜 첫 실행에서는 늘 건너뛰어 하루 한 번 도는 운영에서는 영원히 돌지 않는다.

6. **브리핑** (`brief.py`, `report.py`)
   묶음 세 개에서 다섯 개를 골라 마크다운 한 장으로 만들어 `data/briefs/<날짜>.md` 에 남긴다. 어제 기사 수를 최근 이레 평균과 견준 한 줄과(기사가 없는 날은 수집이 돌지 않은 날로 보고 빼며, 출처를 바꾼 `source_since` 앞의 날도 뺀다. 남은 날이 `brief.average_min_days` 보다 적으면 견주지 않는다), 최근 일주일에 없던 키워드가 있으면 그것도 함께 적는다. 앞선 이레 기사가 DB 에 한 건도 없는 실행에서는 처음 보는 키워드 절을 아예 내지 않는다. 빈 DB 에서 세면 관심 키워드 전부가 처음 보는 말이 되어 매일 거짓을 적게 되기 때문이다. 묶음이 상한을 넘어 잘렸을 때와 `brief.min_groups` 보다 적을 때도 그 사실을 한 줄로 적는다. 월요일에는 `data/reports/<주 시작일>/report.md` 와 `keywords.png` 를 더 만든다. 리포트는 키워드 표와 차트, 새로 나온 도구와 규제 목록, 사람이 채우는 코멘트 절, 한계, 그리고 맨 아래 출처 절로 이루어진다. 같은 주를 다시 만들어도 사람이 코멘트 절에 적은 줄은 그대로 옮겨 오고, 만든 날짜를 본문에 적지 않아 같은 입력이면 파일이 같다.

7. **전송** (`notify.py`)
   브리핑을 슬랙 웹훅으로 보낸다. 기본값은 미리보기라 아무것도 바깥으로 나가지 않고 내용만 파일과 로그에 남는다. 실제로 보내려면 `--no-dry-run` 을 붙인다. 노션은 자리만 만들어 두었고 아직 꺼져 있다.

## 설치와 실행

파이썬 3.13 이면 바로 돈다. 가상환경을 따로 만들지 않아도 되지만 만들어 쓰는 편이 깔끔하다.

```bash
# 차트를 그릴 때만 필요하다. 브리핑까지는 표준 라이브러리로만 돈다.
python3 -m pip install matplotlib

# 어제치를 받아 브리핑까지 만든다. 전송은 미리보기로 끝난다.
python3 -m news_brief run

# 날짜를 짚어 돌린다.
python3 -m news_brief run --date 2026-09-11

# 단계만 따로 돌린다.
python3 -m news_brief collect --date 2026-09-11   # 받아서 DB 에 넣기만
python3 -m news_brief qa      --date 2026-09-11   # 쌓인 것만 점검
python3 -m news_brief brief   --date 2026-09-11   # 받아 둔 자료로 브리핑만
python3 -m news_brief report  --week 2026-09-07   # 그 주 월요일부터 한 주 리포트

# 실제로 슬랙에 보낸다. 웹훅 주소가 환경변수에 있어야 한다.
python3 -m news_brief run --no-dry-run
```

### GDELT 를 부르지 않고 돌려 보기

망을 타지 않고 전 단계를 돌려 볼 수 있다. `tests/fixtures/gdelt_<한국날짜>.json` 에 저장해 둔 응답을 GDELT 대신 읽는다. 시연할 때와 구간 쪼개기를 눈으로 볼 때 쓴다.

```bash
python3 -m news_brief run --date 2026-09-11 --dry-run --fixtures tests/fixtures
```

지금 들어 있는 픽스처는 넷이다. 2026-09-10 하루 12건과 2026-09-11 하루 21건은 손으로 지어낸 표본이라 링크가 실제 기사로 이어지지 않는다. 2026-09-09 하루 250건과 2026-09-12 하루 76건은 실제로 받은 응답이다. 자세한 내용은 `tests/fixtures/README.md` 와 `tests/fixtures/실응답_출처.md` 에 적어 두었다.

프로젝트 폴더를 건드리지 않고 돌려 보려면 `--root` 로 다른 자리를 준다. 그 자리에 `config` 폴더만 복사해 두면 DB 와 산출물이 전부 거기로 떨어진다.

```bash
python3 -m news_brief run --date 2026-09-11 --root /tmp/시험뿌리 --fixtures tests/fixtures
```

### 지금 저장소에 든 자료

이 저장소를 열어 보면 브리핑과 리포트, DB 가 이미 들어 있다. 그것이 어디서 나온 것인지 분명히 적어 둔다.

| 자리 | 무엇인가 |
| --- | --- |
| `tests/fixtures/gdelt_2026-09-10.json`, `gdelt_2026-09-11.json` | GDELT 응답 모양을 흉내 낸 표본이다. 실호출로 받은 응답이 아니고 손으로 지어낸 값이다. 12건과 21건이다 |
| `tests/fixtures/gdelt_2026-09-09.json`, `gdelt_2026-09-12.json` | 2026-09-13 에 GDELT DOC API 를 실제로 불러 받은 응답이다. 250건과 76건. 질의와 구간은 `tests/fixtures/실응답_출처.md` 에 적어 두었다 |
| `data/briefs/2026-09-09.md`, `2026-09-12.md` | 실제로 받은 GDELT 응답으로 만든 브리핑이다. 발송 기록은 없다 |
| `data/briefs/2026-09-13.md` 부터 | GitHub Actions 가 날마다 만들어 슬랙과 노션으로 보낸 브리핑이다. 09-13 은 DOC API 로, 09-14 부터는 GDELT 원본 파일(GKG)에서 받았다 |
| `data/sent/*.txt` | 날마다 언제 어느 실행이 보냈는지 남긴 기록이다. 같은 날을 두 번 보내지 않는 근거로 쓴다 |
| `data/reports/2026-09-07/` | 지어낸 표본으로 돌린 DB 에서 만든 주간 리포트와 차트다. 실제 기사가 아니다 |
| `data/reports/2026-09-14/` | GitHub Actions 가 실제 수집분으로 만든 첫 주간 리포트다 |
| `data/news.db`, `data/raw/`, `data/evidence/` | 저장소에 올리지 않는다. 로컬과 러너에서만 쌓인다 |

실제 응답으로 만든 브리핑의 링크는 실제 기사로 이어진다. 지어낸 표본과 그것으로 만든 2026-09-07 주간 리포트는 그렇지 않다. 다만 제목의 키워드만 보고 AI 소식을 가려낸 결과가 사람 판단과 얼마나 맞는지, 곧 분류 정확도는 아직 재지 않았다. 자세한 갈래는 `tests/fixtures/README.md` 에 적었다.

### 시험

```bash
python3 -m unittest discover -s tests
```

시험은 400개가 넘고 3초 남짓에 다 돈다. 망을 타는 시험은 하나도 없다. 링크를 실제로 받아 보는 점검도 시험에서는 가짜 부르개를 물려 확인한다.

### 자주 쓰는 옵션

| 옵션 | 하는 일 |
| --- | --- |
| `--date YYYY-MM-DD` | 다룰 한국 날짜. 안 주면 어제 |
| `--backend rules\|llm` | 판단을 규칙으로 할지 모델로 할지. 안 주면 설정을 따른다 |
| `--dry-run` / `--no-dry-run` | 전송을 미리보기로 끝낼지 실제로 보낼지 |
| `--fixtures 폴더` | GDELT 를 부르지 않고 저장해 둔 응답으로 돈다 |
| `--root 경로` | 프로젝트 뿌리를 다른 자리로 본다 |
| `--force` | `run` 과 `brief` 에서는 저장된 판단을 무시하고 다시 판단한다. `report` 에서는 이미 있는 리포트를 덮어쓴다 |
| `-v` | 로그를 자세히 남긴다 |

`--force` 는 언제 필요한가. 키워드 목록을 고친 다음 같은 날짜를 다시 돌릴 때다. 판단은 DB 에 남아 있고 기사가 그대로면 저장된 판단을 다시 쓰기 때문에, 고친 키워드가 먹으려면 다시 판단하게 해야 한다. 기사가 늘어났을 때는 붙이지 않아도 알아서 다시 판단한다.

`report` 의 `--force` 는 뜻이 다르다. 같은 주 리포트를 다시 만들 때, 이미 있는 파일을 덮어쓸지 정하는 옵션이다. 붙이지 않으면 기존 파일을 그대로 두고 그 사실을 화면에 적는다. 사람이 적은 코멘트는 어느 쪽이든 지키므로, `## 사람 코멘트` 아래 인용 블록에 글이 있으면 그 줄을 새 리포트로 옮겨 붙이고 나머지 본문만 새로 쓴다.

종료 코드는 세 가지다. 0은 끝까지 돌았다는 뜻이고, 1은 점검이 실패해 브리핑을 만들지 않고 멈췄다는 뜻이며, 2는 코드나 설정이 어긋나 도중에 멈췄다는 뜻이다. 깃허브 액션이 이 값으로 성공과 실패를 가른다.

## 설정 파일 두 개

설정은 `config` 폴더의 JSON 두 장에 다 모여 있다. 코드를 고칠 일은 없다. 값만 바꾸고 저장하면 다음 실행부터 먹는다. JSON 이라 주석을 달 수 없어서 항목마다 `_설명` 을 붙여 두었다. 그 설명 항목은 코드가 읽지 않으니 지우지 않아도 되고 지워도 된다.

### config/keywords.json 은 효준님이 고치는 파일이다

무엇을 세고 무엇을 버릴지 정하는 낱말 목록이다. 손으로 고칠 일이 가장 잦은 쪽이라 여기만 기억하면 된다. 목록 여섯 개가 들어 있고, 목록마다 바로 위에 `_설명` 이 붙어 있다. 파일을 열면 그 줄부터 읽으면 된다.

| 항목 | 하는 일 | 고치면 무엇이 달라지나 |
| --- | --- | --- |
| `keywords` | 리포트에서 세고 차트에 올릴 관심 키워드. 회사, 모델과 서비스, 주제, 정책 네 갈래로 묶어 두었다 | 주간 리포트의 표와 차트, 브리핑의 처음 보는 키워드 |
| `interest` | AI 소식이 맞는지 가릴 때 쓰는 넓은 목록 | 하나라도 제목에 있으면 브리핑 후보로 남는다 |
| `exclude` | 제목에 있으면 버릴 말 | 증시와 잡다한 꼭지를 걷어낸다. 넓게 적으면 멀쩡한 기사도 사라진다 |
| `regulation` | 규제와 정책 소식을 가릴 말. 부처와 위원회 이름, 입법 절차, 처분을 담는다 | 묶음이 브리핑의 규제와 정책 절로 간다 |
| `tool` | 새 도구와 출시 소식을 가릴 말 | 묶음에 새로 나온 도구 표시가 붙는다 |
| `stopwords` | 제목을 견줄 때 빼는 흔한 말 | 엉뚱한 기사끼리 묶이는 것을 막는다 |

고칠 때 걸리기 쉬운 자리가 세 곳이다.

첫째, 제목 글자를 그대로 견주므로 띄어쓰기가 다르면 못 센다. `AI 기본법` 과 `AI기본법` 처럼 갈리는 말은 둘 다 적어 둔다. 실제로 둘 다 적어 두었다.

둘째, 낱말 경계를 보는 잣대가 글자 종류에 따라 다르다. `LG` 나 `AI` 처럼 로마자와 숫자로만 된 말은 앞뒤에 경계를 두고 찾으므로 `algorithm` 안의 `lg` 나 `AIDS` 안의 `AI` 에 걸리지 않는다. 한글이 섞인 말은 낱말 첫머리에서만 센다. 그래서 `삼성` 은 `삼성전자` 도 세지만 `메타` 는 `메타버스` 를 세지 않는다. 한국어는 조사가 낱말에 그대로 붙기 때문에 뒤쪽은 막지 않았다.

셋째, `keywords` 에 한쪽이 다른 쪽을 품는 말을 둘 다 적으면 한 기사가 두 번 세어져 표가 부푼다. 그래서 `GPT` 는 `keywords` 에서 뺐다. `챗GPT` 기사가 `GPT` 로도 세어져 표에서 `GPT` 가 늘 더 많게 나오기 때문이다. 거르는 데 쓰는 `interest` 에는 그대로 두었다. 거기서는 넓게 걸리는 편이 낫다. 서로를 품는 짝이 새로 들어오면 `tests/test_config.py` 의 `test_세는_목록에_서로를_품는_낱말이_없다` 가 잡아 준다.

고친 다음에는 `--force` 를 붙여 같은 날짜를 다시 돌려 보면 무엇이 달라지는지 바로 보인다.

### config/settings.json 은 숫자와 이름을 모아 둔 파일이다

파이프라인이 쓰는 값이다. 한 번 정해 두면 자주 건드리지 않는다. 자주 보게 되는 것만 적으면 이렇다.

| 열쇠 | 기본값 | 무엇인가 |
| --- | --- | --- |
| `query` | `("artificial intelligence" OR OpenAI) sourcelang:korean` | GDELT 검색어. `sourcelang:korean` 이 한국어 기사만 남긴다 |
| `maxrecords` | 250 | GDELT 가 한 번에 주는 상한. 올려도 더 오지 않는다 |
| `sleep_seconds` | 5 | 요청 사이에 쉬는 시간. 더 빨리 부르면 429 로 막힌다 |
| `max_split_depth` | 4 | 상한에 걸린 구간을 반으로 쪼개는 깊이. 코드가 5에서 끊는다 |
| `judge.backend` | `rules` | 판단을 규칙으로 할지 모델로 할지 |
| `judge.similarity_threshold` | 0.4 | 제목이 이만큼 겹치면 같은 사건으로 묶는다 |
| `brief.min_groups` / `max_groups` | 3 / 5 | 브리핑에 올릴 묶음 개수. 대표 묶음과 규제 묶음까지 합쳐 센다 |
| `brief.max_keywords` | 8 | 처음 보는 키워드를 몇 개까지 적을지. 끊은 개수는 `외 N개` 로 밝힌다 |
| `qa.volume_low_ratio` / `volume_high_ratio` | 0.5 / 2.0 | 건수가 평균의 이 아래나 위면 주의 |
| `qa.max_drop_ratio` | 0.7 | 판단이 이 비율 넘게 걸러내면 주의 |
| `qa.max_stray_ratio` | 0.1 | 한국 날짜를 벗어난 기사가 이 비율을 넘으면 멈춘다 |
| `qa.link_check.enabled` | `false` | 링크가 가리키는 곳의 제목까지 받아 볼지. 이 점검만 망을 탄다 |
| `notify.dry_run` | `true` | 참이면 보낼 내용만 만들고 실제로는 보내지 않는다 |
| `paths.*` | `data/...` | 산출물이 떨어지는 자리 |

파일을 고치지 않고 환경변수로 덮어쓸 수도 있다. `NEWS_BRIEF_QUERY`, `NEWS_BRIEF_MAXRECORDS`, `NEWS_BRIEF_BACKEND`, `NEWS_BRIEF_DRY_RUN` 같은 이름을 쓴다. 표에 없는 자리는 `NEWS_BRIEF_CFG__judge__model` 처럼 두 밑줄로 이어 적는다. 비밀값은 두 파일 어디에도 적지 않는다.

## 자동 점검 열한 가지

`qa.py` 가 아래를 본다. 앞의 다섯 가지는 받아 온 것만으로 볼 수 있어서 적재 전에 한 번 보고, 적재와 판단을 마친 뒤에 열한 가지를 다시 본다. 실패가 하나라도 있으면 브리핑을 만들지 않고 멈춘다. 주의는 사람이 한 번 들여다볼 일이지 멈출 일은 아니라서 그대로 지나간다.

| 점검 | 무엇을 보나 | 어긋나면 |
| --- | --- | --- |
| 수집 건수 | 기사가 한 건이라도 모였는지 | 실패. 검색어나 시간 구간이 어긋난 것이다 |
| 상한 구간 | 250건 상한에 걸린 채 남은 구간이나 GDELT 가 막아 못 받은 구간이 있는지 | 실패. 남은 만큼 기사를 놓쳤다. 두 까닭을 갈라 적는다 |
| 날짜 범위 | 기사 시각을 한국 시간으로 바꿨을 때 대상 날짜 안에 드는지. 벗어난 것은 수집기가 넣기 전에 버리고 그 건수를 점검이 본다 | 버린 기사가 받아 온 건수의 `qa.max_stray_ratio` 를 넘으면 실패, 그 아래면 주의 |
| 필수 필드 | 링크, 제목, 매체, 시각이 다 있는지 | 실패. 응답 모양이 달라진 것이다 |
| 링크 중복 | 같은 기사를 가리킨 링크가 두 줄로 남았는지 | 실패. 걸러내기가 새고 있다 |
| 판단 대조 | 판단이 다룬 건수가 DB 에 쌓인 건수와 같은지 | 실패. 브리핑 본문과 건수가 서로 다른 하루를 말하게 된다 |
| 적재 대조 | 모은 건수와 DB 에 쌓인 건수가 맞는지 | 주의. 어느 쪽으로 어긋나도 두 숫자를 함께 적는다 |
| 기록 이어짐 | 앞선 이레 기사가 DB 에 남아 있는지 | 주의. 없으면 처음 보는 키워드 절을 비운다 |
| 최근 이레 대비 | 건수가 앞선 이레 평균의 절반 아래나 두 배 위인지. 평균은 기사가 있는 날, 출처를 바꾼 뒤의 날로만 낸다 | 주의. 주말과 연휴에는 실제로 줄어든다 |
| 걸러낸 비율 | 판단이 너무 많이 걸러냈는지 | 주의. 제외 낱말이 너무 넓다는 신호다 |
| 기사 링크 대조 | 링크가 가리키는 곳의 제목이 기사 제목과 겹치는지 | 주의. 기본은 꺼져 있다 |

판단 대조를 실패로 둔 까닭이 있다. 판단은 DB 에 쌓인 하루치로 돌고 브리핑의 기사 수도 DB 를 센다. 두 숫자가 갈리면 본문에는 없는 기사가 건수에만 들어가 있는 브리핑이 나간다. 같은 날짜를 다시 수집해 기사가 늘었는데 저장해 둔 옛 판단을 그대로 쓴 경우가 그렇다. 판단 쪽이 링크 묶음을 견주어 알아서 다시 판단하도록 고쳐져 있으니 이 점검이 걸릴 일은 드물지만, 그 그물이 뚫렸을 때 어긋난 브리핑을 막는 마지막 자리다. 걸리면 `--force` 로 다시 판단하면 된다.

날짜 범위를 비율로 보는 까닭이 있다. GDELT 는 기사 시각을 15분 단위로 끊어 주기 때문에 하루 경계에 놓인 기사 한 건이 반올림만으로도 옆날로 보인다. 그 한 건에 하루 산출물을 통째로 걸지 않으려고 임계값을 두었다. 경계 계산이 크게 틀어진 경우는 비율로도 그대로 걸린다. 한 건도 넘기고 싶지 않으면 `qa.max_stray_ratio` 를 0 으로 둔다.

임계값 아래 한두 건은 그냥 넘기는 것이 아니라 수집 단계에서 버린다. 넘겨 주면 DB 에 잘못된 날짜로 들어가고, `store` 는 링크를 기본키로 써서 한 번 들어간 기사의 날짜를 나중 실행이 덮어쓰지 않는다. 그러면 원인을 고친 뒤에도 그 기사는 영원히 잘못된 날에 매달려 일별 건수와 주간 리포트에 섞인다. 그래서 수집기가 구간 밖 기사를 스스로 걸러 내고 버린 건수를 결과에 담아, 점검이 그 숫자를 비율로 보고 주의나 실패를 낸다. 점검 표에 오르는 "경계에 걸친 기사를 수집 단계에서 걸러 냈다" 가 그 줄이다.

링크 중복은 원본 링크 글자가 아니라 점검이 따로 만든 열쇠로 견준다. `http` 와 `https` 의 차이, `www.`, 끝의 빗금, `utm_` 같은 추적 파라미터만 지우고 기사 번호가 든 파라미터는 그대로 둔다. 원본 글자를 그대로 견주면 수집 단계가 이미 합친 뒤라 어떤 경우에도 걸리지 않는다.

기사 링크 대조는 기본이 꺼짐이다. 켜려면 `qa.link_check.enabled` 를 참으로 둔다. 이 점검만 바깥으로 요청을 내보내고, 저장소에 든 픽스처는 기사 번호를 손으로 지어낸 것이라 켜 두면 늘 어긋남으로 나온다. 켜면 상태 코드만 보지 않는다. 없는 기사 번호에도 200 과 틀만 남은 페이지를 돌려주는 매체가 있어서, 응답의 `title` 을 꺼내 기사 제목과 낱말이 겹치는지까지 본다. 겹침이 `qa.link_check.min_overlap` 아래면 어긋난 링크로 센다. 어긋나도 주의로만 남기고 멈추지는 않는다.

시각을 한국 날짜로 바꾸는 계산은 `qa.py` 가 `config.py` 를 빌리지 않고 직접 한다. 링크 열쇠도 `collect.py` 의 것을 빌리지 않고 따로 만든다. 수집이 쓴 자와 점검이 쓴 자가 같으면 그 자가 틀어졌을 때 아무도 알아채지 못한다.

## 사람과 기계와 AI 가 맡는 일

**기계가 맡는 일.** 일정에 맞춰 GDELT 를 부르고, 구간을 쪼개고, 겹친 링크를 줄이고, DB 에 쌓고, 열한 가지를 점검하고, 브리핑 파일을 만들고, 슬랙으로 보내고, 도중에 멈추면 왜 멈췄는지 알리는 일이다. 여기까지는 사람이 손댈 자리가 없다. 같은 날짜를 다시 돌려도 같은 결과가 나오도록 판단을 저장해 두는 일도 기계 쪽이다.

**AI 가 맡는 일.** 제목만 보고 AI 소식인지 가려내고, 같은 사건을 다룬 제목끼리 묶고, 묶음에 한 줄 문장을 붙이는 일이다. `judge.backend` 가 `llm` 일 때만 모델을 부른다. 기본값은 `rules` 라서 아무 열쇠가 없어도 파이프라인 전체가 돈다. 모델을 부르는 경로가 어긋나면 곧바로 규칙으로 내려앉고 그 사실을 브리핑 아래에 적는다. AI 는 여기 한 자리에만 들어간다. 수집, 점검, 브리핑 문장 틀은 모델을 쓰지 않는다. 모델이 없어도 파이프라인이 멈추지 않게 하려는 것이다.

**사람이 맡는 일.** 브리핑을 읽고 판단하는 일, 그리고 `config/keywords.json` 을 손보는 일이다. 무엇이 우리에게 중요한 소식인지는 코드가 정할 수 없다. 놓친 소식이 보이면 `interest` 에 말을 더하고, 엉뚱한 기사가 올라오면 `exclude` 에 더한다. 점검이 주의를 낸 날 그게 진짜 이상인지 주말 탓인지 가리는 일도 사람 몫이다. 비밀값을 시크릿에 넣는 일, 그리고 실제 전송을 켜는 결정도 사람이 한다.

## 한계

솔직하게 적어 둔다. 아래는 고치지 못한 것이 아니라 이 방식이 원래 못 하는 것들이다.

**GDELT 가 훑지 않는 매체가 있다.** GDELT 는 자기가 수집하는 매체 목록 안에서만 기사를 돌려준다. 목록에 없는 매체의 기사는 아무리 중요해도 여기 올라오지 않는다. 어떤 매체가 목록에 있고 없는지는 GDELT 가 밝히지 않아서 우리 쪽에서 확인할 길도 없다. 브리핑에 특정 매체가 늘 안 보인다면 그 매체를 GDELT 가 안 훑는 것일 수 있다. 그럴 때는 이 파이프라인으로 메울 수 없고 다른 수집 경로가 필요하다.

**한 번에 250건이 상한이다.** 상한에 걸리면 시간 구간을 절반으로 쪼개 다시 받는데, 기본 네 번까지만 쪼갠다. 90분 토막에서도 250건이 차는 날이 있으면 그만큼 놓친다. 놓친 것을 모르고 지나가지는 않는다. 점검이 실패로 멈추고 어느 구간이 남았는지 알려 준다. 대처는 이렇다. `max_split_depth` 를 다섯까지는 올릴 수 있고 그보다 크게 적으면 코드가 다섯으로 끊고 경고만 남긴다. 깊이 하나를 올릴 때마다 요청 수가 배로 늘고 요청마다 5초를 쉬므로, 깊이 다섯이면 최악에 요청 63번, 스물두 분이다. 깃허브 액션의 `timeout-minutes: 30` 안에 겨우 든다. 그래서 다섯에서 끊었다. 그래도 상한 구간이 남으면 깊이 대신 검색어를 좁히거나 하루를 반씩 나눠 두 번 돌려야 한다.

**본문을 보지 않고 제목만 본다.** GDELT 는 기사 제목과 링크만 준다. 본문을 가져오려면 매체마다 긁어야 하고 그건 이 프로젝트가 하지 않기로 한 일이다. 그래서 제목이 낚시면 판단도 같이 어긋난다. 제목에 AI 가 안 적힌 AI 소식은 놓치고, 제목만 AI 인 광고성 기사는 남는다. 링크가 열린다는 것만으로 제목이 맞다고 할 수도 없다. 지어낸 기사 번호로 실제 매체를 받아 보니 없는 번호에도 200 과 빈 페이지를 돌려주는 매체가 있었고, 엉뚱한 기사에 닿는 경우도 있었다. 자세한 대조는 `data/evidence/2026-09-11_대조.md` 에 있다.

**규칙 판단과 모델 판단은 잘하는 자리가 다르다.**

| | `rules` | `llm` |
| --- | --- | --- |
| 무엇으로 가리나 | 키워드 목록에 있는 말이 제목에 있는지 | 제목을 읽고 무슨 소식인지 |
| 열쇠가 필요한가 | 아니다 | `ANTHROPIC_API_KEY` 가 있어야 한다 |
| 같은 입력에 같은 결과 | 그렇다 | 아니다. 문장이 조금씩 달라진다 |
| 값 | 0원 | 하루 한 번, 제목 수십 줄 분량 |
| 잘하는 자리 | 목록에 적은 말은 절대 놓치지 않는다 | 목록에 없는 말로 적힌 소식을 알아본다 |
| 못하는 자리 | 목록에 없는 말로 적힌 소식은 통째로 놓친다 | 묶음 문장을 지어내는 쪽으로 기울 수 있다 |

기본값을 `rules` 로 둔 까닭이 여기 있다. 하루 한 번 도는 일에서 중요한 것은 어제와 오늘의 숫자를 견줄 수 있다는 점이고, 같은 입력에 같은 결과가 나오지 않으면 견줄 수가 없다. 모델 판단은 놓친 소식을 줄이려고 할 때 켠다. 둘을 함께 쓰고 싶으면 `--force --backend llm` 으로 같은 날짜를 다시 판단해 두 브리핑을 견줘 보면 된다.

**실데이터로 아직 확인하지 못한 자리가 있다.** 하루치가 250건 상한에 걸려 구간을 쪼개는 경로는 실제 GDELT 응답으로 확인하지 못했다. 요청 하나에 15초 남짓 걸리고 앞에 5초를 쉬므로 구간이 여러 개로 나뉘면 한 번 실행이 몇 분씩 가고, 그 사이 GDELT 가 429 로 막는 일도 있었다. 쪼개기 자체는 하루 620건짜리 표본을 만들어 상한을 실제 값 250 으로 두고 `tests/test_collect_live.py` 에서 확인했지만, 실제 응답으로 확인한 것과는 다르다. 상한에 걸리는 날이 실제로 있는지, 그때 몇 토막까지 나뉘는지도 아직 모른다.

**실제 발송은 2026-09-13 치부터다.** 그 뒤 브리핑은 GitHub Actions 가 날마다 실제로 돌려 보낸 것이고 발송 기록이 `data/sent` 에 남는다. 지어낸 표본에서 나온 것은 픽스처 두 파일과 2026-09-07 주간 리포트뿐이다. 어느 파일이 무엇인지는 위 [지금 저장소에 든 자료](#지금-저장소에-든-자료) 에 표로 적었다. 실제 발송분이라도 AI 소식인지는 제목의 키워드로만 가른 것이라, 분류 정확도와 운영 전후의 시간 절감량은 재지 않았다.

## 비밀값

값은 코드와 설정 파일 어디에도 적지 않는다. 환경변수와 깃허브 시크릿으로만 넣는다. 로그에 남을 때는 앞 두 글자만 남기고 가린다.

| 이름 | 무엇에 쓰나 | 없으면 |
| --- | --- | --- |
| `SLACK_WEBHOOK_URL` | 브리핑과 실패 알림을 보낼 슬랙 웹훅 주소 | 보내지 않고 내용만 파일과 로그에 남는다 |
| `NOTION_TOKEN` | 노션 통합 토큰 | 노션에 쌓지 않는다. 지금은 기본이 꺼져 있다 |
| `NOTION_PARENT_PAGE_ID` | 노션에서 페이지를 만들 부모 페이지 | 같다 |
| `ANTHROPIC_API_KEY` | `--backend llm` 으로 판단할 때 부르는 모델 열쇠 | 규칙 판단으로 내려앉는다 |

넷 다 없어도 파이프라인은 끝까지 돈다. 그 경우 판단은 규칙으로 하고 전송은 미리보기로 끝난다.

### 내 컴퓨터에서 넣는 방법

```bash
export SLACK_WEBHOOK_URL="https://hooks.slack.com/services/..."
export ANTHROPIC_API_KEY="sk-ant-..."
python3 -m news_brief run --no-dry-run --backend llm
```

값을 파일에 적어 두려면 `.env` 를 만들어 쓴다. 이미 `.gitignore` 에 들어 있어서 저장소에 올라가지 않는다. 다만 이 프로젝트는 `.env` 를 읽는 코드를 넣지 않았으니 셸에서 `set -a; . ./.env; set +a` 처럼 직접 불러와야 한다.

### 깃허브 액션에 넣는 방법

저장소의 Settings, Secrets and variables, Actions 로 들어가 New repository secret 을 눌러 위 이름 그대로 넣는다. 워크플로가 이름으로 집어 가므로 파일을 고칠 필요는 없다. `ANTHROPIC_API_KEY` 가 있으면 판단을 모델로 하고 없으면 규칙으로 한다. 손으로 돌릴 때는 Actions 탭에서 workflow_dispatch 로 날짜와 미리보기 여부를 골라 줄 수 있다.

전송은 시크릿만으로 켜지지 않는다. 같은 화면의 Variables 탭에서 `SEND_FOR_REAL` 을 `true` 로 만들어야 실제로 슬랙에 나간다. 웹훅 주소를 저장소에 넣는 일과 매일 아침 실제로 보내기로 정하는 일은 다른 결정이라, 시크릿을 한 번 넣은 것만으로 다음 날부터 전송이 시작되면 설정 파일만 읽은 사람은 아직 미리보기라고 믿게 된다. 그래서 기본은 어느 경로에서나 미리보기다. 예약 실행도, workflow_dispatch 에서 미리보기를 끈 경우도, 이 변수가 없으면 미리보기로 남는다.

### 액션은 DB 를 캐시로 이어 간다

깃허브 액션은 실행마다 저장소를 새로 받으므로, 그냥 두면 `data/news.db` 가 매번 사라지고 아침마다 기사 0건에서 시작한다. 그러면 최근 이레 평균, 처음 보는 키워드, 주간 리포트가 모두 빈 기록 위에서 돌아 이 프로젝트가 내세우는 시계열 대목이 하나도 남지 않는다. 그래서 `actions/cache` 로 DB 파일 하나를 실행 사이에 이어 간다. 실행마다 `news-db-<실행 번호>` 로 새로 저장하고, 다음 실행은 `news-db-` 로 시작하는 가장 최근 것을 되살린다. 커밋이 아니라 캐시를 고른 까닭은 sqlite 파일이 매일 커지는 이진 파일이어서, 저장소 역사에 하루치씩 쌓으면 받아 올 때마다 무거워지기 때문이다.

이 선택의 대가는 이렇다.

- 캐시는 백업이 아니다. 깃허브는 이레 동안 쓰이지 않은 캐시를 지우고, 저장소 전체 캐시가 10GB 를 넘으면 오래된 것부터 밀어낸다. 사람이 Actions 화면에서 지울 수도 있다.
- 캐시가 비면 그 실행은 빈 DB 로 돈다. 그때는 브리핑이 처음 보는 키워드 절을 아예 내지 않고 왜 비웠는지 한 줄을 남긴다. 점검 표에도 `기록 이어짐` 이 주의로 뜬다. 없는 이력을 있는 척하지 않는 쪽을 골랐다.
- 캐시는 브랜치 단위로 갈린다. 기본 브랜치에서 돌린 기록을 다른 브랜치의 실행이 읽을 수는 있지만 그 반대는 되지 않는다.
- 앞선 실행과 뒤 실행이 겹치면 한쪽 기록이 덮일 수 있다. 워크플로에 `concurrency` 를 두어 겹쳐 도는 것을 막아 두었다.
- 이력을 오래 남겨야 할 만큼 쌓이면 캐시 대신 다른 자리로 옮겨야 한다. 지금 규모에서는 캐시로 충분하다.

## 자료 출처

기사 목록은 GDELT Project 의 DOC 2.0 API 에서 받는다. 이 프로젝트가 가지고 있는 것은 GDELT 가 준 제목과 링크, 매체 이름, 시각뿐이고 기사 본문은 받지도 쌓지도 않는다. 브리핑에 실린 링크의 저작권은 각 매체에 있다.

- GDELT Project: https://www.gdeltproject.org/
- DOC 2.0 API 문서: https://blog.gdeltproject.org/gdelt-doc-2-0-api-debuts/

GDELT 는 키가 필요 없는 공개 API 지만 요청을 5초에 한 번으로 제한한다. 이 프로젝트는 그 간격을 지키고, 그래도 막히면 쉬고 다시 부른다. 검색어를 넓혀 요청 수를 크게 늘리는 쪽으로 고칠 때는 GDELT 쪽 안내를 한 번 읽어 보는 편이 좋다.


## 매일 실행을 거는 방법

GitHub 예약(schedule)은 보장이 없다. 2026-09-14 에는 09:00, 12:37, 14:37 예약이 뜨지 않았고 16:37 예약은 1시간 37분 늦게 떴다. 그래서 매일 실행은 맥의 launchd 가 GitHub API 로 워크플로를 불러 시작한다. 워크플로 파일의 GitHub 예약은 보조로 남겨 두었다.

- 등록 파일: `~/Library/LaunchAgents/com.kimhyojun.ai-news-brief.plist`
- 시각: 매일 09:00 부터 11:40 까지 20분마다 (맥 시간대 기준). 브리핑은 아침 9시에 받기로 했다
- 실행 스크립트: `~/Library/Application Support/ai-news-brief/trigger.sh` 가 `gh workflow run daily.yml -f dry_run=false -f auto=true` 를 부른다. 11시 이후 실행은 `last=true` 를 붙인다
- 기록: `~/Library/Logs/ai-news-brief/trigger.log`
- 맥이 그 시각에 잠들어 있었으면 깨어난 직후 한 번 누른다. 깨자마자는 인터넷이 아직 안 붙어 있을 수 있어서, GitHub 에 닿을 때까지 최대 3분 기다리고 요청이 실패하면 30초 뒤 두 번 더 해 본다. 맥이 하루 종일 꺼져 있으면 그날은 GitHub 보조 예약만 남는다
- `DRY=1` 을 붙여 스크립트를 부르면 연결만 확인하고 실제로 누르지는 않는다

auto 를 켠 실행은 그날 브리핑을 이미 보냈으면(`data/sent/<날짜>.txt`) 바로 끝난다. 그래서 하루에 여러 번 눌러도 한 번만 나간다. 실패 알림은 마지막 시도에서만 슬랙으로 간다.

자동 실행은 한국 시각 9시부터 11시 59분 사이에만 보낸다. 2026-09-15 저녁 8시 37분 GitHub 예약이 네 시간 밀려 자정을 넘겨 도는 바람에 대상 날짜가 하루 넘어갔고, 9월 15일 브리핑이 새벽 12시 40분에 나갔다. 아침에 받기로 한 브리핑이 한밤에 나가지 않도록 늦게 도는 실행은 그냥 건너뛴다. 사람이 손으로 돌리는 실행은 이 시각을 보지 않는다.

다른 맥에서 다시 걸 때는 `gh auth login` 을 한 뒤 위 스크립트와 plist 를 같은 자리에 두고 `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.kimhyojun.ai-news-brief.plist` 를 실행한다. 멈출 때는 `bootstrap` 대신 `bootout` 을 쓴다.


## 출처를 바꾼 까닭

처음에는 GDELT DOC 2.0 API 를 불렀다. 그런데 2026-09-14 부터 GitHub Actions 러너에서 부르면 429 로 막히거나, 몇 분 기다려 겨우 통과해도 기사 0건이 돌아왔다. 러너 IP 를 여러 사용자가 같이 써서 우리 요청 간격과 상관없이 막히는 것이다. 9월 15일 새벽과 아침에 네 번 연속 이렇게 멈췄다.

같은 데이터가 `data.gdeltproject.org/gdeltv2/<시각>.translation.gkg.csv.zip` 으로 15분마다 올라오고, 이 파일 서버는 막히지 않는다. 하루치 96개를 받아 원문 언어가 한국어(`srclc:kor`)이고 제목(`PAGE_TITLE`)에 AI 관련어가 든 기사만 남긴다. 9월 14일 치로 돌려 보니 파일 96개를 31초에 다 받았고, 한국어 기사 4,061건 가운데 339건이 남았다.

달라진 점이 셋 있다. AI 소식인지를 본문이 아니라 제목으로 먼저 고른다. 250건 상한이 없어 하루치를 통째로 받는다. 받지 못한 파일이 8개를 넘으면 점검이 그날을 멈춘다. 예전 API 경로는 `config/settings.json` 의 `source` 를 `gdelt_doc` 으로 바꾸면 그대로 쓸 수 있다.
