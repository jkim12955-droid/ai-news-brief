# 이어받기 안내

이 자동화를 다른 사람이, 또는 다른 Claude 계정에서 이어서 손볼 때 먼저 읽는 문서다.
무엇이 어디서 도는지, 손대기 전에 알아야 할 결정과 그 까닭, 아직 남은 일을 적었다.
코드가 어떻게 돌아가는지는 `README.md` 에 있다. 이 문서는 그 위의 맥락만 담는다.

## 한 줄 요약

매일 아침 9시, 어제 하루치 한국어 AI 기사를 모아 점검하고 묶어서 슬랙, 노션, 깃허브 세 곳으로 보낸다.
데이터 분석 직무 포트폴리오로 쓰려고 만들었고, 2026-09-13 부터 매일 실제로 돌고 있다.

## 매일 실행이 누구 손에 달려 있나

깃허브 예약(schedule)은 몇 시간씩 늦거나 아예 빠진다. 그래서 실제로 실행을 누르는 건 효준님 맥이다.

1. 맥 launchd 가 아침 9:00 부터 11:40 까지 20분마다 `~/Library/Application Support/ai-news-brief/trigger.sh` 를 부른다. 등록 파일은 `~/Library/LaunchAgents/com.kimhyojun.ai-news-brief.plist`, 기록은 `~/Library/Logs/ai-news-brief/trigger.log` 다.
2. 깃허브 예약 `cron: "37 0,1,2 * * *"`(한국 9:37, 10:37, 11:37)은 보조다.

여러 번 눌려도 `data/sent/<날짜>.txt` 가 있으면 워크플로가 바로 끝나서 브리핑은 하루에 한 번만 나간다.
자동 실행은 한국 시각 9시부터 11시 59분 사이에만 보낸다. 사람이 손으로 돌리는 실행은 이 두 가지를 보지 않는다.

**맥을 옮기거나 다른 사람이 맡으면** 그 맥에서 `gh auth login` 을 한 번 하고, 위 두 파일을 같은 자리에 두고
`launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.kimhyojun.ai-news-brief.plist` 를 실행한다.
멈출 때는 `bootstrap` 대신 `bootout` 이다. 맥이 그 시각에 잠들어 있었으면 깨어난 직후 한 번 누른다.

## 비밀값

저장소 시크릿에 세 개(`SLACK_WEBHOOK_URL`, `NOTION_TOKEN`, `NOTION_PARENT_PAGE_ID`)와 저장소 변수 `SEND_FOR_REAL=true` 가 들어 있다.
시크릿은 저장소에 붙어 있어서 사람이나 Claude 계정이 바뀌어도 그대로 간다. 값은 저장소 설정에서 꺼내 볼 수 없고, 바꿀 때만 새로 넣는다.
`SEND_FOR_REAL` 이 true 가 아니면 실행이 미리보기로만 끝난다. 시크릿이 비어 있어도 미리보기로 끝난다. 그래서 받아서 바로 돌려도 남의 슬랙으로 뭔가 나가지 않는다.

슬랙에 보이는 발신자 이름과 아이콘은 코드가 아니라 슬랙 앱 설정에서 바꾼다. https://api.slack.com/apps 에서 Basic Information 의 Display Information 과 App Home 의 App Display Name 둘 다 고쳐야 한다.

## 손대기 전에 알아야 할 결정

**기사를 깃허브 API 가 아니라 원본 파일에서 받는다.** 2026-09-15 에 GDELT DOC 2.0 API 가 깃허브 러너에서 네 번 연달아 막혔다(429 와 빈 응답). 러너 IP 를 여러 사용자가 같이 쓰는 탓이라 우리 쪽에서 간격을 늘려도 소용없었다. 같은 데이터가 15분마다 파일로도 올라오고 그 파일 서버는 막지 않아서 `news_brief/gkg.py` 로 하루치 96개를 받아 직접 거른다. 되돌리려면 `settings.json` 의 `source` 를 `gdelt_doc` 으로 바꾸면 된다. 못 받은 파일이 여덟 개를 넘으면 점검이 그날을 멈춘다. 구멍 난 하루를 조용한 날로 착각하지 않으려는 것이다.

**제목만 보고 고른다.** GDELT 는 본문을 주지 않는다. 그래서 묶음 문장도 제목을 다듬어 쓰고, 브리핑 맨 아래에 제목만 봤다는 한계를 적는다. 이 한계 문장을 지우지 않는다.

**브리핑은 어제 하루치다.** 하루 경계를 한국 시간으로 끊는다. 오늘 아침 9시에 오늘 기사를 받으면 아홉 시간짜리 토막으로 "몇 매체가 다뤘나"를 세게 되고 날짜별 집계가 어긋난다. 2026-10-22 에 이 방식을 그대로 두기로 정했다.

**최근 평균은 기사가 있는 날로만 낸다.** 수집이 돌지 않은 날을 0건으로 넣으면 평소 수준의 날이 평균의 몇 배로 보인다. 출처를 바꾼 날(`source_since`, 2026-09-14) 앞의 기록도 뺀다. 그때는 하루 건수 규모가 달랐다. 견줄 날이 세 개보다 적으면 아예 견주지 않는다.

**같은 날을 다시 돌려도 결과가 같아야 한다.** 기사는 링크를 기본키로 넣고, 한 번 들어간 기사의 날짜는 나중 실행이 덮어쓰지 않는다. 판단 결과도 DB 에 남기고 집계는 저장본으로 한다. 이 성질을 깨는 수정은 하지 않는다.

**묶기 규칙은 건드리지 않기로 했다.** 하루 묶음이 270개쯤 나오는 게 많아 보이지만, 2026-09-15 에 세어 보니 대부분 한 매체만 다룬 서로 다른 기사였다. 글자 쌍 유사도로 더 묶어 봤더니 야구 기사 연재가 한데 묶여서 되돌렸다.

**글은 AI 티 없이 쓴다.** 줄표(—)와 이모지를 쓰지 않는다. 브리핑과 리포트 문장은 사람이 쓴 것처럼 담백하게 쓴다. 숫자는 실제로 센 값만 적는다.
