# 지적 39건 검증 상태

수리 담당 셋이 고친 것을 대조 담당이 코드와 시험으로 다시 확인한 기록이다. 보고에 적힌
말이 아니라 지금 저장소의 코드가 하는 일을 기준으로 판정했다. 확인한 날은 2026-09-13 이다.

상태는 셋이다.

- 고쳐짐: 코드나 시험, 실제 실행 출력으로 확인했다
- 미뤄짐: 지금 환경에서 확인할 수 없거나 효준님이 결정할 몫이다
- 남아 있음: 고쳐지지 않았고 미룰 까닭도 없다

## 이 표를 읽을 때 알아 둘 것

확인은 모두 픽스처와 시험으로 했다. GDELT 실호출은 하지 않았다. `tests/fixtures` 의
세 파일 가운데 `gdelt_2026-09-10.json` 과 `gdelt_2026-09-11.json` 은 손으로 지어낸
표본이고 링크가 실제 기사로 이어지지 않는다. `gdelt_2026-09-12.json` 한 건만 실제로
받아 둔 응답이다. 그래서 파이프라인이 이어진다는 것과 같은 입력에 같은 결과가
나온다는 것까지는 확인되지만, 브리핑에 오른 기사가 실제 기사와 맞는지는 이 표의 어느
줄로도 말할 수 없다. 그런 줄에는 상태를 미뤄짐으로 적고 까닭을 밝혔다.

## 이번 대조에서 고친 것

수리 담당 셋이 남긴 자리 가운데 셋을 대조 담당이 이어 고쳤다.

1. 붙임표와 범위 밖 기호(30번). `brief._text`, `judge._글다듬기`, `report._clean_text` 세 곳에
   `_HYPHENS` 를 넣어 U+2010 과 U+2011 을 아스키 붙임표로 내리고, `_EMOJI` 에 U+2122 와
   U+2139 를 더했다. 붙임표를 쉼표로 바꾸지 않은 까닭은 `GPT‑5` 가 `GPT, 5` 가 되면 뜻이
   달라지기 때문이다. 화살표와 ▶ 는 한국어 제목에서 뜻을 지고 와서 건드리지 않았다.
   세 모듈이 같은 값을 내는지 보는 시험을 새로 넣었다.
2. 구간 밖 기사 버리기(16번과 28번의 틈). 두 지적이 서로 반대쪽을 가리켜서, 순서를 바꾸고
   비율 임계값을 넣은 뒤에도 임계값 아래 한두 건은 여전히 DB 에 잘못된 날짜로 들어갔다.
   `collect_day` 가 하루 구간 밖 기사를 넣기 전에 버리고 `stray_dropped` 와 `stray_samples` 로
   들고 나오게 했다. `qa._check_dates` 는 그 숫자를 비율로 보아 임계값 아래면 주의,
   넘으면 멈춤을 낸다. DB 에서 읽어 온 하루(`qa` 명령)는 예전처럼 기사 목록을 훑는다.
3. 처음 보는 키워드를 비운 까닭(13번의 나머지). 집계가 담아 준
   `first_seen_skipped_reason` 을 읽는 코드가 아무 데도 없어서 신호가 끊겨 있었다.
   절만 조용히 사라지면 읽는 사람은 어제 새 말이 하나도 없었다고 읽는다.
   `brief._history_note` 로 그 까닭을 본문과 슬랙 블록에 한 줄 적게 했다.

문서도 두 곳 고쳤다. `tests/fixtures/README.md` 와 `README.md` 가 픽스처 전부를 손으로
지어낸 것이라고 적어 두었는데, 실응답 한 건이 들어온 뒤로 사실과 달랐다. 어느 파일이
실측이고 어느 파일이 지어낸 것인지 갈라 적었다.

## 저장소에 남은 산출물은 고침 이전 것이다

코드는 고쳐졌지만 `data` 폴더의 파일은 고치기 전에 만든 것이라 새 문장을 들고 있지 않다.
표의 상태는 코드를 기준으로 판정했고, 이 파일들은 손대지 않았다.

- `data/reports/2026-09-07/report.md` 에는 "2026-09-12에 만들었다" 가 남아 있고, 빈 날 목록에
  아직 오지 않은 날이 섞여 있으며 맨 아래 "## 출처" 절이 없다. 25번, 9번, 3번 고침 이전 판이다
- `data/briefs/2026-09-11.md` 의 처음 보는 키워드 절에는 여덟 개가 적혀 있고 "외 N개" 꼬리가
  없다. 2번 고침 이전 판이다. DB 에 09-10 자료가 있어 이 절 자체는 거짓이 아니다
- 두 파일 모두 사람이 채운 코멘트가 없어서 다시 만들어도 잃을 것은 없다

## 효준님이 결정할 것

1. `data/news.db` 의 2026-09-10, 09-11 자료. 지어낸 픽스처로 만든 것이라 실데이터와 섞이면
   구분이 안 된다. 지울지, 그대로 두고 실데이터는 다른 뿌리에서 돌릴지 정해야 한다.
2. 같은 DB 에 남은 빈 `decisions` 표와 그 색인. 스키마에서는 빠졌지만 이미 만들어진 파일에는
   남아 있다. 사람 자료가 든 파일에 `DROP TABLE` 을 자동으로 돌리지 않았다.
3. `config/keywords.json` 의 GPT 와 챗GPT. 낱말 경계를 고쳐도 챗GPT 기사가 GPT 로도 한 번 더
   세진다. 목록 설계 문제라 갈래를 나누거나 한쪽을 빼야 한다. LG 도 `LG전자`, `LG유플러스` 처럼
   늘려 적는 편이 안전하다.
4. 실호출을 언제 할지. 250건 상한 쪼개기와 두 주 비교 표, 모델 판단 산출물은 모두 실호출이나
   API 열쇠가 있어야 남는다. 지금 표에서 미뤄짐으로 적힌 네 줄이 그것이다.
5. 깃허브 저장소 변수 `SEND_FOR_REAL`. 실제로 슬랙에 보내려면 이 변수를 `true` 로 켜야 한다.
   켜기 전에 미리보기 산출물을 한 번 더 읽어 보는 편이 좋겠다.
6. `data` 폴더의 브리핑과 리포트를 지금 코드로 다시 만들지. 위에 적은 대로 세 가지 고침이
   그 파일에 반영되어 있지 않다. `report --week 2026-09-11 --force` 와
   `run --date 2026-09-11 --force --fixtures tests/fixtures` 를 돌리면 바뀌지만, DB 와
   효준님 자료를 건드리는 일이라 대조 담당이 손대지 않았다.
